# 原生工具保留

## 为什么这是个真问题

BYOK 一旦接管了 agent 端点，**决定上游模型看到哪些工具的就是本工具**。Cursor 的原生工具——文件读写、终端、语义检索、浏览器自动化等——是客户端在请求里声明的。如果本地服务用自己的工具列表替换掉它们，会发生这样的事：

- 聊天看起来完全正常，模型照样回话
- 但模型再也不会调用 `read_file` 或 `run_terminal_cmd`，因为它根本不知道这些工具存在
- 用户会以为是"模型变笨了"，而不会想到工具列表被换掉了

这是一个**静默失效**。正因为静默，它不能靠约定或代码评审保证，必须写成不变式。

## 两条路，两种机制

这一点很容易踩空：**"保留原生工具"在两条路径上的做法是相反的。**

| | OpenAI 兼容入口 | Cursor agent 端点 |
|---|---|---|
| 工具从哪来 | 客户端在请求里声明 | **协议里定义，请求里根本没有** |
| 服务端要做的 | 原样转发，一个字节不许改 | **自己推导目录，并把模型的调用映射回类型化消息** |
| 失效的样子 | 工具被替换，模型不再调用 | 目录没生成，模型以为自己没有工具 |

下面的不变式管的是第一条路。第二条路的机制见 [agent回话.md](agent回话.md)——`agent.v1.ToolCall` 是约 70 个具名消息的 closed oneof，工具目录从描述符自动推导（3.14.7 上 47 个），不是转发来的。

## 不变式

`packages/core/src/tools/registry.ts` 的 `ToolRegistry` 定义：

1. **原生工具原样存储。** 客户端声明的 `name` / `description` / `parameters` 一字不改，连原始载荷（`raw`）也保留，避免在本工具的内部表示里绕一圈造成有损转换。
2. **增补只能追加，不能覆盖。** `augment()` 遇到已存在的名字时记为 `shadowed` 并跳过，绝不替换。
3. **顺序稳定。** 原生工具按声明顺序在前，增补工具在后。顺序稳定对上游的 prompt 缓存有实际意义。
4. **同名原生工具保留首次声明。** 与主流工具调用 API 的冲突解决方式一致。

```ts
const registry = ToolRegistry.fromNative(clientDeclaredTools, policy);
const report = registry.augment(serverSideTools);
// report.shadowed 里是被原生工具挡住的服务端工具 —— 这是正常结果，不是错误
const tools = registry.list();   // 原生在前，增补在后
```

## 策略开关

```jsonc
{
  "tools": {
    "preserveNative": true,        // 关掉后丢弃客户端工具集（瘦客户端场景）
    "allowAugmentation": true,     // 关掉后服务端不追加任何工具
    "augmentationDenyList": [],    // 即使允许增补也永不追加的名字
    "nativeAllowList": []          // 工具列表被裁剪时必须保留的原生工具
  }
}
```

`preserveNative: false` 是一个**显式的**支持路径（面向确实没有原生工具的瘦客户端），而不是意外。单元测试里单独断言了这个行为，让它保持可见。

## 一个容易忽略的细节：Gemini 会拒绝它不认识的 JSON Schema 关键字

Cursor 的原生工具 schema 里含有 `additionalProperties`、`$schema` 之类的关键字。Gemini 的 `functionDeclarations` 对未实现的关键字会直接报错，导致**整个请求失败**——于是所有原生工具一起不可用。

`packages/providers/src/adapters/gemini.ts` 里的 `stripUnsupportedSchema` 递归保留 Gemini 支持的关键字、丢掉其余部分。丢关键字是有损的（比如 `additionalProperties: false` 的约束没了），但代价明确：保住工具可用，而不是让请求整体失败。

这类差异**只在适配器内部消化**，`ToolRegistry` 交给适配器的永远是原始 schema。

## 路由表层面的保留

工具保留不只在 agent 端点。路由表本身也刻意留了几处直通：

| 端点 | 为什么不接管 |
|---|---|
| `aiserver.v1.AnalyticsService/BootstrapStatsig` | 特性开关（feature gate）配置。接管后返回空会让一部分原生工具面被关掉，所以只接管了 `AnalyticsService/Batch`（遥测上报），`BootstrapStatsig` 直通官方 |
| `aiserver.v1.DashboardService/ListMarketplacePlugins` | 插件市场发现。`DashboardService` 是**逐方法**挂规则的，没列出的方法自动直通 |
| 任何未在方法注册表里认识的方法 | 默认 `upstream`，因为官方 API 还知道怎么处理 |

单元测试里对这三条有显式断言（`test/unit/routing.test.mjs` 的最后一个用例），防止有人图省事把 `AnalyticsService` 或 `DashboardService` 整个服务加进路由表。

## 实测验证

`pnpm verify:e2e` 在 **provider 边界**上验证，也就是检查 mock provider 实际收到的请求，而不是相信构造它的代码：

```
[PASS] every native tool reached the provider, in declaration order
       — read_file, run_terminal_cmd, codebase_search
[PASS] native tool description survived unchanged
       — "Read a file from the workspace"
[PASS] native tool JSON Schema survived unchanged
       — {"type":"object","properties":{"path":{"type":"string"},
          "offset":{"type":"integer"}},"required":["path"],
          "additionalProperties":false}
```

注意第三条里 `additionalProperties: false` 完整保留——OpenAI 路径不做 schema 裁剪。

单元测试（`test/unit/tools.test.mjs`，8 个用例）覆盖：原生工具身份与顺序、增补无法替换原生（冒名的 `IMPOSTOR` 描述被挡住）、顺序关系、增补总开关、deny list、同名去重、`assembleTools` 组合、`preserveNative: false` 的显式行为。
