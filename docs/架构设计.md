# 架构设计

## 一、问题是什么

Cursor 的模型能力由它自己的后端提供。要换成自有密钥，必须在**请求离开 Cursor 进程之前**把它拦下来。Cursor 是 Electron 应用，请求可能从五类进程发出：

| 进程 | 文件 | 运行时 |
|---|---|---|
| 渲染进程（聊天界面） | `out/vs/workbench/workbench.desktop.main.js`（38.7 MB） | 浏览器 |
| 渲染进程（glass 变体） | `out/vs/workbench/workbench.glass.main.js`（45.8 MB） | 浏览器 |
| 扩展宿主 | `out/vs/workbench/api/node/extensionHostProcess.js`（3.7 MB） | Node |
| 本地服务工具进程 | `out/vs/code/electron-utility/alwaysLocalSingleton/alwaysLocalSingletonMain.js`（2.3 MB） | Node |
| Agent Host（子代理） | `extensions/cursor-agent-host/dist/main.js`（6.7 MB） | Node |

以上是在 Cursor 3.14.7 上**按内容指纹实测**得到的结果，不是硬编码的清单——`packages/patcher/src/detect/discover.ts` 会扫描所有候选文件，只把真正含有 `api2.cursor.sh` / `aiserver.v1.` / `agent.v1.AgentService` 等指纹的文件当作目标。这样某个版本把传输层挪到别的进程时，发现逻辑仍然找得到。

## 二、分层

```
                       ┌──────────────────────────────┐
                       │  cli  /  extension           │  入口层
                       └───────────┬──────────────────┘
                                   │
      ┌────────────────────────────┼────────────────────────────┐
      │                            │                            │
┌─────▼─────┐              ┌───────▼───────┐            ┌───────▼───────┐
│  patcher  │              │    server     │            │  interceptor  │
│  安装器    │              │  本地 BYOK    │            │  注入运行时    │
└─────┬─────┘              └───┬───────┬───┘            └───────┬───────┘
      │                        │       │                        │
      │                 ┌──────▼──┐ ┌──▼────────┐               │
      │                 │providers│ │ protocol  │               │
      │                 └────┬────┘ └─────┬─────┘               │
      │                      │            │                     │
      └──────────────────────┴────────────┴─────────────────────┘
                                   │
                            ┌──────▼──────┐
                            │    core     │  纯领域层，无副作用依赖
                            └─────────────┘
```

依赖只从上往下。`core` 不依赖任何其他包，因此渲染进程载荷（浏览器环境，没有 `fs`）也能直接复用它的路由逻辑。

### core — 共享基础

- `config/` 配置模型、归一化、原子读写、带**保留上一可用版本**语义的热更新 store
- `routing/` 路由规则语法、编译后的路由表、主机匹配器、统一决策器
- `tools/` 原生工具保留的不变式（见 [原生工具保留.md](原生工具保留.md)）
- `tls/` 纯 Node 实现的 ASN.1/X.509 自签证书生成器（socket 层需要本地 TLS 监听）
- `net/` HTTP/1.1 与 h2c 在同一端口上的协议多路复用器

### interceptor — 注入运行时

真正的劫持逻辑，写成普通 TypeScript 模块，由 esbuild 打成两份自包含 IIFE：

- `dist/payload.runtime.cjs`（67 KiB）注入 Node 进程，用静态 import 让 esbuild 生成 `require("node:...")`，天然适配 Cursor 的 CJS 包
- `dist/payload.renderer.js`（18 KiB）注入渲染进程，只改 `fetch` 与 `WebSocket`，配置在打补丁时内联并通过 SSE 热更新

这是与原工具最大的工程差别：原工具把载荷写成巨大的 JS 模板字符串，无法类型检查也无法单测；这里载荷是真实源码，单测与集成验证都能直接覆盖。

### patcher — 安装器与 schema 提取器

打补丁是四个环节一条流水线：**发现 → 计划 → 应用 → 校验**，失败整体回滚。

`schema/` 子目录承担另一件事：从安装目录里恢复 Cursor 的 protobuf 描述符。它属于 patcher 而不是 protocol，因为"读 Cursor 的文件"是 patcher 的职责；两者的边界是描述符文档的格式，该类型定义在 protocol 里。

**所有补丁都只是"在文件前面加一段"**，不改写任何表达式。由此得到一个极强的校验条件：打过补丁的文件必须逐字节等于 `载荷 + 原文`。这比重新解析 AST 更强也更便宜，也是 `applyPlan` 敢在单个文件出问题时整体回滚的依据。

原工具需要 AST 手术的几件事，这里换成了别的环节：

| 原工具的 AST 手术 | 本工具的替代 |
|---|---|
| 把 `nal_websocket_client` 字面量改掉以禁用 Agent WebSocket | 把 `/agent/v1/run` 当成普通路由规则，由服务按策略拒绝升级 |
| 在扩展 `activate` 里注入 30 秒阻塞等待 | 劫持层用异步 `createConnection` / `lookup` 逐请求挂起 |
| 把 `if(!x.valid)` 改成 `if(!1)` 绕过扩展签名校验 | 服务不放进内置扩展目录，无需绕过 |

### server — 本地 BYOK 服务

同时监听两个端口，因为两类劫持层送来的流量形态不同：

- **明文端口**：HTTP/1.1 + h2c（协议多路复用器嗅探 HTTP/2 preface 区分），给路径感知的那几层
- **TLS 端口**：ALPN 协商 `h2` / `http/1.1`，给 socket 层——它在还没有路径时就捕获了连接，无法降级成明文

请求分发顺序：控制端点 → WebSocket 升级（按策略）→ REST 桩 → ConnectRPC 方法（按策略）→ **其余全部反代回官方**。最后这一步是"保留原生行为"的机制所在。

哪些方法在本地应答是有标准的：**转发会静默出错的，才本地接管**。`AvailableModels` 不接管就看不到自己的模型；`RunSSE` / `BidiAppend` 不接管就没有 BYOK；知识库不接管的话，add 会报成功而 list 是空的——用户会以为功能坏了而不是不可用。其余方法即便在路由表里，只要 handler 不确定自己答得对，就退回转发。

### providers — 模型适配

一个泛化接口进，一条扁平事件流出。OpenAI 适配器按线格式而非厂商 SDK 编写，所以换个 `baseUrl` 就能服务 DeepSeek、OpenRouter、Groq、本地 vLLM 等所有兼容端点，而不是每家一个适配器。

## 三、几个关键取舍

### 为什么把捕获点下移到 socket 层

只改 `http.request` 会漏掉三类客户端：走 HTTP/2 的 ConnectRPC 传输、打包进 bundle 的 undici（不经过 `globalThis.fetch`）、自带 WebSocket 实现的库。原工具的应对是改写 bundle 让 HTTP/2 分支不可达——每个版本都要重新定位。

本工具在 `net.connect` / `tls.connect` 上兜底，代价是此时还没有路径，只能按主机判定；换来的是**新传输层无法静默绕过**。代价由服务端消化：未命中路由的请求如实反代回官方。

### 为什么"保持请求不变、只改 socket 去向"

HTTP/1.1 层不重写 URL、不改 Host、不动 body，只用异步 `createConnection` 决定 socket 连到哪里。由此：

1. 服务还没起来的请求可以**挂起等待**，而不是让用户的第一句 prompt 失败；
2. 服务始终没起来时，**同一个请求对象**连到官方 API 就能成功，因为它从未被改写过——字节语义与未安装本工具时完全一致。

这一点在实测里单独验证：服务不存在时三种客户端全部成功回落官方；服务延迟 2 秒启动时请求成功等到了服务。

### 为什么服务是独立进程

把服务放进 Cursor 内置扩展目录能拿到生命周期管理和侧边栏 UI，但必须改掉扩展签名校验——这是比"前置一段载荷"侵入性大得多的改动。本工具选择让服务独立运行，生命周期交给三种可选方式：终端里跑、可选扩展拉起、注册成系统服务。可选扩展是普通用户扩展，不需要任何签名绕过。

### 协议层：结构化编解码 + 从安装里恢复的 schema

Cursor 的 `.proto` 未公开，所以协议层分两层。

底层是 `protocol/wire` 的**结构化**编解码：protobuf 线格式自带字段号与 wire type，足以在完全不知道 schema 的情况下还原消息形状。由此得到三个不依赖 schema 的能力——空消息是任何消息类型的合法编码（这正是账号/看板类端点该给的回复）、未知消息可被渲染成字段树以便逆向、只改其中一个字段后可原样重编码。

上层是 `protocol/schema` 的**描述符驱动**编解码，把字节与以 camelCase 为键的普通对象互转。描述符不是硬编码的，而是 `patcher/schema` 在安装时**从用户自己的 Cursor 里提取**的：Cursor 用 `@bufbuild/protobuf` 做代码生成，它的产物里每个消息是一张字段表、每个服务是一个方法签名对象，完整 schema 一直就在安装目录里。3.14.7 上提取到 5,381 个消息、486 个枚举、72 个服务、1,564 个方法，耗时 820 毫秒。

这样做的三个后果：本仓不含 Cursor 的任何接口定义；描述符永远与实际安装的版本匹配；Cursor 升级由重新提取解决而不是由本仓发版解决。

提取结果经过独立来源交叉校验——18,279 个共有字段零处不一致。详见 [schema恢复.md](schema恢复.md)。

无论哪一层，不认识的方法都默认**转发上游**，因为官方 API 还知道怎么处理。没有描述符时也一样：绝不用猜出来的字段号作答。

### 原生工具在两条路上的机制是相反的

OpenAI 兼容入口上，客户端在请求里声明工具，服务端原样转发——不变式是"不许改"。

Cursor 的 agent 端点上没有工具列表：工具是**协议级**的，`agent.v1.ToolCall` 是一个约 70 个具名消息的 closed oneof，客户端实现、服务端挑选。所以那条路上服务端必须**自己生成工具目录**，并把模型按名字发回的调用**映射回类型化消息**。目录是从描述符自动推导的（3.14.7 上 47 个），因此 Cursor 升级新增工具时会自动出现。

同一个需求，两种完全不同的实现，细节见 [agent回话.md](agent回话.md) 与 [原生工具保留.md](原生工具保留.md)。
