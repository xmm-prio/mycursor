# 网络劫持

## 为什么需要六层

一个 Node 进程里发 HTTPS 请求有很多条路，它们**不共享同一个函数**：

| 客户端 | 实际调用链 | 只改 `http.request` 能拦住吗 |
|---|---|---|
| `https.request` | `https.request` → `https.Agent.prototype.createConnection` → `tls.connect` | 能 |
| `http2.connect` | `http2.connect` → `tls.connect` | **不能** |
| `fetch`（Node 内置） | undici → `net.connect` / `tls.connect` | **不能** |
| 打包进 bundle 的 undici | 自带副本 → `net.connect` / `tls.connect` | **不能**，连 `globalThis.fetch` 也绕过 |
| `ws` 包 | `https.request` 发 Upgrade | 能，但路径需在路由表内 |
| 自带 WebSocket 实现 | 直接 `tls.connect` | **不能** |

原工具只改 HTTP/1.1，为了让 HTTP/2 与 WebSocket 不被选中，需要用 AST 改写 Cursor 的压缩包（把 `nal_websocket_client` 字面量替换、把 accepted-origin 数组清空）。这两处都依赖压缩产物里的具体形状，每个版本都要重新定位。

本工具改为分六层拦截，每层可独立开关：

```
┌─ http1      http.request / https.request / http.get / https.get
├─ http2      http2.connect
├─ fetch      globalThis.fetch
├─ websocket  globalThis.WebSocket
├─ socket     net.connect / tls.connect / net.createConnection
│             + http.Agent.prototype.createConnection
│             + https.Agent.prototype.createConnection
└─ dns        dns.lookup（默认关闭，逃生通道）
```

## 两个必须踩过才知道的坑

这两处都是实测发现并修掉的，值得单独记下来。

### `agent: false` 不等于"没有 agent"

HTTP/1.1 层的整个设计建立在 `options.createConnection` 上。但 Node 只在**完全没有 agent** 时才使用它：

```js
// Node 内部逻辑（简化）
if (agent === false) {
  agent = new defaultAgent.constructor();   // 新建一个默认 agent！
} else if (agent === null || agent === undefined) {
  if (typeof options.createConnection !== 'function') agent = defaultAgent;
  // createConnection 存在时，agent 保持 undefined
}
```

写 `agent: false` 会让 Node **新建**一个默认 agent，于是 `options.createConnection` 被忽略，请求按原主机名去做 DNS 解析并直连官方——劫持完全失效，而且失效得很安静。必须把 `agent` **删掉**（置为 `undefined`）。

实测表现：三种 `createConnection` 形态在 `agent: false` 下全部报 `getaddrinfo ENOTFOUND`，改成 `agent: undefined` 后全部成功，包括异步回调形态。

### Node 的 HTTP agent 在模块加载时就抓走了原始函数

`http.js` 与 `https.js` 在首次求值时把 `net.createConnection` / `tls.connect` 装到了 `Agent.prototype.createConnection` 上。注入载荷永远晚于这个时刻，所以**只改模块导出不够**——agent 仍然调用原始函数，`https.request` 会直接穿过 socket 层。

所以 socket 层额外给两个 agent 原型打补丁，并且只接管命中主机的连接，其余仍交还原始实现（会话复用、代理支持都在那里）。

实测表现：只开 socket 层时，`http2`、`fetch`、裸 `tls.connect` 都被正确捕获，唯独 `https.request` 跑到了官方——补上 agent 原型补丁后通过。

另外，`parseConnectArgs` 判断"这是不是 IPC 连接"时不能只看 `options.path` 存在：Node 的 agent 会把 `path` 透传给 `createConnection` 但**置为 `null`**，且总带 port。只看 `path` 会把每一个 agent 发起的连接误判成管道而放过。

## 三个稳定性机制

### 一、请求挂起：同步 API 里藏一个 await

`http.request`、`http2.connect`、`tls.connect` 都同步返回，看起来没有等待服务就绪的余地。但每条路径上都恰好有一个**异步钩子**：

| 层 | 钩子 | 能力 |
|---|---|---|
| http1 | `options.createConnection(options, callback)` | 可以返回 `undefined` 后异步调 callback，**完整自由** |
| http2 | `options.createConnection()` 必须同步返回 Duplex | 返回一个缓冲写入的延迟 Duplex（`deferred-socket.ts`），就绪后再接到真实 socket |
| socket | `options.lookup(hostname, options, callback)` | 异步解析，兼作就绪门控 |

`readiness.strategy: "hold"` 时，请求在这些钩子里等待服务最多 `maxWaitMs`，而不是立刻失败。

> `lookup` 回调有个坑：Node 20+ 默认开 `autoSelectFamily`，会传 `all: true` 并要求返回**地址数组**；返回裸字符串会报 `Invalid IP address: undefined`。

#### 等待只为"正在启动"，不为"根本没有"

这个区分曾经写在 `cached()` 的文档里却没被遵守：它返回 `undefined` 表示"还没探测过，值得等"，返回 `null` 表示"探测过了，那里没有"。而 `waitForTarget` 用 `if (cached) return cached` 把两者当成了同一回事。

后果很严重：Cursor 已经打了补丁而服务起不来时，**每一个请求都先干等 20 秒**再回落官方。实测连发三个请求，各 19.9 秒——用户看到的就是界面一直转圈，而不是"某个功能没生效"。

现在一次等待走完全程仍没等到服务，就记下时刻；在 `probeTtlSeconds` 内后续请求**直接放行（0 毫秒）**，TTL 过后再重新探测一次。修复后同样三个请求：19.9 秒、0 毫秒、0 毫秒。

冷启动语义没有变——服务正在启动时，第一个请求照样等到它为止。`invalidate()` 会清掉这个记录，所以服务后来起来了也能立刻被接回去。

### 二、无损回落：保持请求不变，只改 socket 去向

HTTP/1.1 与 HTTP/2 层都不重写请求本身——Host、路径、body 全部保持原样，只决定 socket 连到哪里。服务始终没起来时，同一个请求对象连到官方 API 就能成功，字节语义与未安装本工具时完全一致。

这里还照顾了一个细节：调用方传进来的 agent 可能携带用户的代理配置。回落时**优先使用它的 `createConnection`**，公司代理后面的用户不会因为本地服务没起来就断网。

### 三、保留上一个可用配置

原工具的配置读取在解析失败时回退到 `emptyState()`——所有劫持规则清零，静默全部直通。编辑器保存文件的瞬间文件可能短暂不合法，这一瞬间的请求就全跑官方了。

本工具的 `ConfigStore` 区分"文件不存在"（合法地用默认值）与"文件不合法"（保留上一个已发布版本），并且：

- watcher 挂在**目录**而非文件上——原子保存会换掉 inode，文件级 watch 会永久失效
- 新版本先解析、归一化、编译路由表，全部成功后才整体切换，读者永远看不到半应用状态

## 层间协作：绕过标记

socket 层按主机捕获，路径感知层按路径判定。若上层已判定"放行"，下层不该再捕获，否则未命中路径会多绕一跳。

机制：Node 把 `http`/`https` 的 options 一路传到 `tls.connect`，所以在上层打一个标记就能传到下层。HTTP/1.1 层放行时会克隆参数并打上标记（URL 形态则插入一个只含标记的 options 对象）。

**一个已知的例外**：undici 自己构造连接参数，标记传不过去。所以 `fetch` 放行的请求仍会被 socket 层捕获，由服务反代回官方——多一跳，结果一致，且路由权威只有一处。这一点在验证矩阵里是显式断言的期望值，不是遗漏。

## WebSocket：用配置代替 AST 手术

Cursor 的 agent 传输可以升级到 `/agent/v1/run` 上的 WebSocket。原工具改写 bundle 让这条分支不可达。

本工具把这个路径当成**普通路由规则**（`REST:/agent/v1/run`）。`ws` 包用 `https.request` 发握手，于是 HTTP/1.1 层直接命中并把它送到本地服务，服务按 `interception.websocketPolicy` 处理：

- `downgrade`（默认）回 426，客户端回落到 SSE 传输
- `route` 由服务实现该端点
- `ignore` 不干预

整件事变成一个配置值，跨版本稳定。`websocket` 层只负责 `globalThis.WebSocket` 这类完全绕过 `http.request` 的客户端。

## 实测结论

`pnpm verify:interceptor` 的 26 项断言覆盖：

- **全层开启**：`https.request`、`https.get`、`http2`、`fetch`、裸 `tls.connect` 五种命中路径全部落到本地服务，且上游主机身份（Host / `:authority` / SNI / 溯源头）至少有一条通道保留；未命中路径保持原生直通；WebSocket 升级被拒绝
- **仅 socket 层**（模拟未知传输层）：四种客户端全部仍被捕获
- **服务不存在**：三种客户端全部无损回落官方 API，且只有第一个请求付等待代价
- **服务延迟启动**：请求挂起等到服务，而非失败
