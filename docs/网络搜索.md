# 网络搜索

BYOK 接管后默认会**丢掉**的一项能力，以及为什么补它比看起来麻烦。

## 一、为什么会丢

Cursor 的网络搜索跑在**它自己的后端**上。模型发出 `web_search` 调用，Cursor 的服务器去搜，把结果塞回对话。客户端全程不参与。

一旦流量被本地服务接管，这条链路断在中间：工具还在协议目录里（`agent.v1.ToolCall` 的 oneof 里就有），模型照样会调，但没有任何一方会去执行它。表现是模型说"我来搜一下"，然后什么都没发生。

## 二、服务端工具和协议工具是两类东西

这是本文的关键区别。

| | 协议工具（`read` / `shell` / …） | 服务端工具（`web_search` / `web_fetch`） |
|---|---|---|
| 谁声明 | 协议里定义 | **本地服务声明** |
| 谁执行 | **Cursor 客户端**（IDE 去读文件、跑命令） | **本地服务自己** |
| 结果怎么回来 | 客户端发起新一轮请求，带着结果 | **必须在同一回合内解决** |

最后一行是整个设计的约束来源。服务端是**按回合无状态**的——对话历史由客户端在每次请求里送来。本地服务往历史里插一条工具结果，客户端下一轮根本不会带上它。所以服务端工具的结果**没有地方可以存活到下一回合**，只能在本回合内被消费掉。

于是 `TurnRunner` 里有一个内层循环：

```
向 provider 要一次回复
  ├─ 模型调了服务端工具 → 本地执行 → 把结果作为 tool 消息追加 → 再问一次 provider
  ├─ 模型调了协议工具   → 转发给客户端，回合结束（IDE 会带着结果发起新请求）
  └─ 模型给了文本       → 流式吐出，结束
```

### 三种边界情况

**混合调用**。模型在一次回复里同时调了协议工具和服务端工具。协议工具已经转发出去、回合即将结束，服务端工具的结果无处可去。此时**记一条 warn 并放弃执行**，而不是执行完把结果丢掉——后者会真的去搜一次、花掉配额、然后什么都不产生。

**无限循环**。模型可能一直搜下去。这段循环对用户完全不可见（没有工具卡片、没法中断），所以硬上限 6 轮，超了就发一条说明并收尾。

**后端失败**。搜索服务 500 了，**返回文本而不是抛异常**。用户正在回合中间，模型看到"搜索失败了"还能换个说法重试；抛异常会把已经生成的内容全部丢掉。

## 三、六个后端

| 后端 | 需要 Key | 搜索 | 读页面 | 端点 |
|---|---|---|---|---|
| DuckDuckGo | 否 | ✓ | | `html.duckduckgo.com/html/` |
| Exa | 是 | ✓ | | `api.exa.ai/search` |
| Tavily | 是 | ✓ | | `api.tavily.com/search` |
| Brave | 是 | ✓ | | `api.search.brave.com/res/v1/web/search` |
| Jina Reader | 是 | ✓ | ✓ | `s.jina.ai` / `r.jina.ai` |
| Firecrawl | 是 | ✓ | ✓ | `api.firecrawl.dev/v1/{search,scrape}` |

**DuckDuckGo 是默认**，因为它是唯一不用注册的：打开开关就应该能用，而不是先跳去申请一个 Key。代价是它没有官方 API，只能解析 HTML，所以解析写成"解不出就返回空结果"而不是抛异常——空结果让模型换个思路，异常会中断回合。

它的结果链接是 `duckduckgo.com/l/?uddg=…` 的跳转形式，**要拆开还原成真实 URL**：否则模型后续每次 `web_fetch` 都会穿过跳转器，而且光看 URL 也判断不出自己要读的是哪个站。

`web_fetch` **只在后端能读页面时才提供**（Jina / Firecrawl）。它们把页面在服务端渲染成 Markdown，模型拿到的是正文而不是一堆 `<script>` 和导航栏——这才是这个工具值得存在的理由。

## 四、绝不遮挡原生工具

用户签着 Cursor 账号时，客户端**自己就声明 `web_search`**。这时本地服务的同名工具必须让路，否则模型的搜索会被劫持到这里、而用户本来付费的搜索反而不生效。

机制是现成的：服务端工具走 `ToolRegistry.augment()`，同名时**客户端声明者胜**，被遮挡的记进 `report.shadowed`。本次新增的是**执行侧的同一条不变式**——`assembleTools` 只为 `report.added` 里的名字建立执行映射，所以一个被遮挡的服务端工具在这里**也是不可执行的**。少了这一条，工具列表里是客户端的定义，实际执行的却是服务端的实现。

`augmentationDenyList` 里的名字同样既不进列表也不可执行。

## 五、配置

默认**关闭**：它会把用户的查询发给第三方，这应该是一个决定，而不是某天突然开始发生的事。

```jsonc
{
  "webSearch": {
    "enabled": false,
    "backend": "duckduckgo",   // duckduckgo | exa | tavily | brave | jina | firecrawl
    "apiKey": "",
    "maxResults": 5,           // 1–20
    "allowFetch": true,        // 后端支持时同时提供 web_fetch
    "proxyUrl": ""
  }
}
```

面板里有对应的一张卡片。需要 Key 的后端才显示 Key 输入框——给一个不需要注册的后端摆一个空的必填框，会让本来能用的默认配置看起来没配完。

搜索走和 provider 调用同一套 HTTP 传输，所以 `proxyUrl` 支持 CONNECT 隧道。

## 六、验证

`pnpm verify:websearch` 断言 38 项。六个后端**代码不做任何修改**地跑起来：它们构造真实的 `api.exa.ai` URL、设置真实的鉴权头、解析真实的 HTTP 响应，只有对端是 mock。

mock 以**HTTP 代理**的形式介入（自己终结 CONNECT 隧道再做 TLS），而不是改 DNS——这样既不需要特权端口，又顺带验证了工具自带的代理路径。

```
── Every backend runs against its own real URL
  [PASS] duckduckgo reached its own endpoint and parsed the reply — html.duckduckgo.com/html/
  [PASS] exa reached its own endpoint and parsed the reply — api.exa.ai/search
  … 六个后端

── Credentials go where each service expects them
  [PASS] exa sends its key as x-api-key — exa-key
  [PASS] brave sends its key as x-subscription-token — brave-key
  … 五个需要 Key 的后端

── Result shaping
  [PASS] the DuckDuckGo redirect was unwrapped to the real URL — 1. Node.js fs & docs
  [PASS] HTML entities in titles were decoded

── Cursor's own tools still come first
  [PASS] a client-declared web_search is not replaced by the server one
  [PASS] a shadowed server tool is not executable here either
  [PASS] the deny list keeps the tool out and unexecutable

── The model's call is resolved inside the turn
  [PASS] the server tool call never reached the client — 0 forwarded
  [PASS] the provider was asked again with the result appended — user,assistant,tool
  [PASS] the tool message carried the search output
```

最后两条是回合内循环的关键证据：**服务端工具调用一次都没有转发给客户端**，而 provider **被带着工具结果重新问了一遍**。
