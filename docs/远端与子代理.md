# 远端与子代理

需求里单独点出的两个场景：**subagent** 与 **ssh remote agent** 的请求稳定性。这两者在 Cursor 里是不同的问题，处理方式也不同。

## 一、Subagent：Agent Host 进程

Cursor 3.13 起把 agent 执行放进了一个独立的内置扩展 `cursor-agent-host`，入口 `extensions/cursor-agent-host/dist/main.js`（3.14.7 上 6.7 MB）。子代理运行时的请求从这个进程发出，**不经过渲染进程也不经过扩展宿主**，所以只给渲染进程打补丁的方案完全覆盖不到它。

在 3.14.7 上按内容指纹实测，它是唯一一个入口包含 Cursor API 指纹的内置扩展：

```
   6.67 MB  cursor-agent-host  ./dist/main.js
            hits: api2.cursor.sh api3.cursor.sh api4.cursor.sh
                  gcpp.cursor.sh aiserver.v1. agent.v1.AgentService
```

其余 114 个内置扩展的入口都不含指纹，安装器会跳过它们——这一点在沙箱验证里是显式断言的。

处理方式与其他 Node 进程完全一致：前置同一份 `payload.runtime.cjs`，`processLabel` 记作扩展名。因为发现是按内容指纹做的，将来 Cursor 把 agent 传输挪到 `cursor-agent-worker` 或 `cursor-local-agent-runtime`，发现逻辑仍然找得到，不需要改代码。

每个目标有独立的 guard 标记（如 `__mycursorGuard_extension_cursor_agent_host`），`doctor` 因此能分辨"哪些进程真的加载了载荷"，而不是从文件内容反推。

### 稳定性

子代理的特殊之处是**它的生命周期比窗口短**。一次子代理运行可能在本地服务还没起来时就开始发请求，也可能在服务重启期间被中断。三个机制针对这一点：

1. **逐请求挂起**。子代理的第一个请求不会因为服务没就绪而失败，它会在 `createConnection` 里等待，最多 `readiness.maxWaitMs`。
2. **无损回落**。等待超时后，同一个请求连到官方 API 仍然成功——请求从未被改写。
3. **会话 rendezvous 而非队列**。Cursor 的 agent 协议把一次对话拆成两个调用：`RunSSE` 开流后等待，`BidiAppend` 带着真正的请求从另一个调用过来，靠 request id 关联。两者谁先到都有可能，所以 `SessionRegistry` 按 request id 做汇合点：先到的消息排队等 `RunSSE`，先到的 `RunSSE` 挂起等消息。会话**只按 request id 索引，不按连接**，因此两个调用走不同传输层时仍能正确配对。
   - 原工具在自己的错误文案里提示过这个坑（"RunSSE waited for the first BidiAppend message but none arrived. This is usually a client-side routing issue"）——配对失败的表现是 prompt 一直不回复直到超时。
4. **无人认领的会话会被清理**。窗口关掉、子代理被杀掉的情况下，`BidiAppend` 的载荷不会泄漏到进程生命周期结束。

### 子代理跑哪个模型

稳定性之外还有一个语义问题：子代理运行是独立的一次请求，靠 `subagentTypeName` 表明身份，而用户常常给它配了一个更便宜的模型。把每次子代理都送到主模型上不会报错，只是更慢更贵。

解析顺序是 `forceDefaultModel` → 按名字键控的 `subagentModelOverrides` → 子代理定义自带的 `model` → 只有一项时的 `selectedSubagentModels`。`CustomSubagent.tools` 非空时工具集还会被收窄——只读的子代理不能拿到 `shell`。细节与验证见 [agent回话.md](agent回话.md) 的第二点七节。

## 二、SSH Remote：跨机器的可达性问题

这是一个本质不同的问题。Cursor 的 remote 场景下：

- 扩展是 `ui` kind 的会跑在**本地**
- 但工作区的扩展宿主、agent host 跑在**远端机器**上

远端进程即使被打了补丁，`127.0.0.1:39841` 在远端指向的是远端自己的回环地址——本地的 BYOK 服务在那里不可达。

### 处理方式：远端也打补丁 + 端口转发回连

安装器不区分"本地"和"远端"，它枚举本机上所有 Cursor 安装：

```
~/.cursor-server/cli/servers/*/server/     每个版本一个目录
~/.cursor-server/bin/*/                    旧布局
```

两种布局共享 `out/` + `extensions/` + `product.json` 的目录结构，所以同一套发现、打补丁、备份、校验和逻辑直接适用。在远端机器上跑同一个 `npx . install` 即可。

`~/.cursor-server` 的位置可以用 `MYCURSOR_CURSOR_SERVER_HOME` 覆盖——有些主机会把它挪走，而且这也是在没有第二台机器时验证远端路径的唯一办法。沙箱验证正是这么做的：按真实 headless 布局构造影子树，只覆盖这一个环境变量，让定位器**靠识别布局**而不是被告知位置。

配置里 `uplink` 决定远端载荷往哪里连：

```jsonc
{
  "uplink": {
    "mode": "auto",     // local → tunnel 依次探测
    "tunnel": { "host": "127.0.0.1", "port": 39841, "tlsPort": 39842 },
    "probeTtlSeconds": 30,
    "probeTimeoutMs": 400
  }
}
```

`mode: "auto"` 时先探 `server`（本机回环），失败再探 `uplink.tunnel`。在远端场景里两者都是回环地址，只是端口可能不同——因为 SSH 反向转发（`ssh -R`）会把本地服务的端口映射到远端回环上。

探测不只看端口是否打开，还要求 `/__mycursor/health` 返回 `{"ok":true,"service":"mycursor"}`。这条身份校验很重要：远端机器上恰好有别的进程占着这个端口时，仅靠 TCP 探活会把模型流量喂给它。

### 失败时的行为

远端连不上本地服务时，**fail-open 直通官方**。远端开发场景里网络本来就更脆弱，让 Cursor 退回它自己的后端比让 prompt 失败要好得多。

### 需要用户做的事

SSH 反向端口转发不是本工具能代劳的，它是连接建立时的参数：

```bash
# 把本地 39841/39842 暴露到远端回环
ssh -R 39841:127.0.0.1:39841 -R 39842:127.0.0.1:39842 user@remote
```

或写进 `~/.ssh/config`：

```
Host remote
  RemoteForward 39841 127.0.0.1:39841
  RemoteForward 39842 127.0.0.1:39842
```

Cursor 的 Remote-SSH 会复用 `~/.ssh/config`，所以写在配置文件里对 Cursor 也生效。

### 另一种选择

若远端本身能访问模型 API，也可以在远端独立跑一份服务：远端 `mycursor install` + `mycursor serve`，配置 `uplink.mode: "local"`，远端自备 `providers.json`。代价是密钥要放在远端机器上。
